MadCop 面试问答准备（产品视角 · vibe coding）
================================================

问1：用一句话介绍 MadCop 是什么产品？
答：MadCop 是一个本地优先的 AI 助手桌面应用。用户用一句话描述需求，Agent 帮他完成：写代码、联网调研、处理文档、生成文件、跑定时任务。它对标 ChatGPT 桌面端和 Codex 这类产品，差异点是"不只是给建议，而是直接在你电脑上把事情做完"，同时所有数据只存在本机。

问2：为什么强调"本地优先"？和 ChatGPT 网页版的差异在哪？
答：一句话：网页版是顾问，MadCop 是驻在本机的员工。顾问给建议，员工直接干活——写好的文件落在你工作目录里，不是贴在聊天框里让你复制；员工了解你的项目，因为他被授权读本地上下文；员工干活你会想有审批，所以每个有风险的动作都有确认卡。而"本地优先"是这一切的前提：用户让 AI 读代码、读个人文件，数据上云的信任成本太高，所以我们承诺除了调用大模型本身，所有数据都留在用户电脑上，界面也用明确的"仅本机"标识说出来。对目标用户，"敢用"比"功能多"更靠前。

问3：产品接的是哪家大模型？
答：不绑定任何一家。MadCop 是多模型可插拔的——用户配置自己的模型供应商，MiniMax、智谱 GLM、DeepSeek、OpenAI、Anthropic 都支持，选哪家用哪家的 Key，随时切换，还有一键接入的快速配置。我的产品观点是：模型层是竞争最激烈、迭代最快的一层，AI 产品不应该替用户锁死模型；产品的价值在于把模型能力稳定地交付成结果，模型只是可替换的零件。

问4：产品的架构参考了什么？
答：站在巨人肩膀上，没有重复发明轮子。交互范式上参考了 Codex、Claude Code 这类成熟 Agent 产品已验证的做法——计划先行、工具调用透明化、敏感操作人工审批、执行中途可以插话调整，这些符合用户心智的范式直接吸收；对话体验对标 ChatGPT 桌面端的标准。MadCop 的原创在于把这套 Agent 能力和"本地执行 + 本地数据"结合，再扩展出知识库、记忆、定时任务这些场景化能力。我的观点是：交互范式不需要原创，需要执行到位；差异化要花在别人没做的位置上。

问5：产品有哪些主要功能？
答：五大块。一是对话主链路：流式回复、工具调用时间线、中途澄清、计划模式；二是文件交付：读写 office 文档、改代码，产物落在用户目录并给一键打开的入口；三是知识体系：知识库、跨会话记忆、知识图谱画布；四是自动化：定时任务和工作流；五是扩展体系：用户可以接入外部工具服务、给 Agent 装新技能。交付原则是"主链路优先"，每个功能都要求能当场演示成功才算完成。

问6：听说这个项目是 vibe coding 做的？具体是怎么工作的？
答：对，整个产品就是我带着 AI 工具做出来的，我是产品和验收的 owner，AI 是实现的主力。我的工作流是：把需求拆成清楚的小任务 → 让 AI 实现 → 我在真实产品上验收 → 发现问题把现象和线索喂回给 AI 修 → 再验。这个循环里最重要的是两件事：一是需求要拆得足够清楚，模糊的任务 AI 只能给出模糊的结果，所以"会提需求"比以前更重要；二是验收必须是真刀真枪的——我坚持每次改动都在打包好的真实产品上把用户路径完整走一遍，从产品、用户、设计三个视角看。vibe coding 改变的不是"要不要写代码"，而是把工程师的重心从"实现"移到了"定义和验收"。

问7：vibe coding 的质量怎么保证？AI 写的代码你敢直接用吗？
答：不敢裸用，所以质量靠流程兜底而不是靠信任。三道闸：第一，验收硬门槛——每个改动都自动化操控真实产品走一遍用户路径，最近一轮全量扫描 23 个界面，揪出 4 个坏页面（显示乱码、整页空白、按钮显示内部代号），全部在用户看到之前修掉；第二，问题必须修到根因——我要求每个修复都讲清楚"症状是什么、根因是什么、怎么验证的"，AI 给的方案如果只修现象我会打回去；第三，小步交付——每个改动独立可回溯，出问题能立刻定位是哪一步引入的。我的观点是：vibe coding 时代代码的生产成本降了，但验证的成本没降，人的价值恰恰在验证那一端。

问8：讲一个印象最深的交付案例。
答：外部工具接入。需求是让用户在设置页填一份工具服务配置，应用立刻获得联网搜索能力。交付时发现配完不好使，排查出好几个叠在一起的问题：界面配置格式和后端读取格式不一致、配置传递破坏了服务启动环境、工具连上了还被权限层挡住模型看不见。都修掉之后还剩一个产品决策：用户配的搜索和内置搜索重名了听谁的？我们定的规则是"用户显式配置的优先于内置默认"——用户主动装的东西就该说话算数。最后端到端验证：聊天里让它搜最新技术动态，真实返回结果并附来源。交付标准就是：修到"规则说得清、结果验得过"，而不是修到"不报错"。

问9：AI 回复不可控，产品上怎么应对？
答：三层。事前定规矩：系统指令明确边界，输出格式做兜底解析，模型偶尔输出乱格式也能自动纠正。事中给透明：流式输出让用户看到它在动，思考过程折叠起来，工具干了什么逐条可见；敏感操作停下来等人确认。事后能追查：出问题有日志有线索，不是无限转圈。还有个产品观：宁可少展示，不展示假的——早期版本显示过"步骤 3/40"这种编造的进度，我们判断编造的进度比没有进度更伤信任，果断全删了。审批的设计也是同一逻辑：AI 要做危险动作时暂停弹出确认卡，可以拒绝、可以只批一次、也可以按目录放行——信任阶梯先严后松，比先出事再补救容易得多。

问10：最棘手的问题是什么？
答：知识画布整页空白。表面是一个 bug，剥出来四层：数据接口读错路径直接报错；页面初始化有时序问题，画布容器还没出现初始化就跳过了；渲染层用了画布不支持的写法，文字全糊成一团；布局引擎失效时静默跳过，兜底方案永远轮不到。四层修完还做了一个产品决策：节点配色从紫色系改成和全局一致的中性色。收获是：一个"空白"背后可能是四个问题，必须修到根因层，修现象层只会反复复发。这类深挖在 vibe coding 里尤其重要——AI 很擅长修"你描述清楚的"问题，所以把现象拆解成清楚的问题描述，本身就是人最关键的工作。

问11：如果给交付质量打分你打多少？不足是什么？
答：85 分以上。扣分三处：一是验收目前靠自动化驱动的人工流程，还没沉淀成自动回归体系；二是一些打磨项还开着，比如个别页面配图风格是旧的、图谱节点密集时文字重叠；三是异常场景的收尾体验，比如中断的任务会在列表里留残影。我把"交付"的定义包含收尾质量，这些是诚实记账的欠债，也是下一阶段的计划。

问12：如果再做三个月，路线图是什么？
答：三件事按顺序。第一，把验收流程沉淀成自动回归体系——这对 vibe coding 尤其关键，AI 写得越快，回归保障越要跟得上，否则速度就是风险；第二，还打磨债：配图、图谱排版、任务残留、异常恢复；第三，为增长做准备：任务完成率埋点和新用户引导。原则不变：先还质量债，再谈新功能。产品的口碑是靠"每个功能都真的能用"攒出来的。

问13：如果面试官质疑"vibe coding 做的产品能算你的能力吗"，你怎么回应？
答：我会说，恰恰相反，vibe coding 对人的要求是更高了而不是更低。写一个功能，实现只占三成，另外七成是：判断什么值得做（产品）、把需求拆解到 AI 能准确执行（定义）、在真实产品里验证它真的可用（验收）、出了问题能顺着现象找到根因（debug）。这四件事 AI 替代不了，而且第二和第四件需要对系统足够的理解才能做好——比如画布那个四层根因的 bug，AI 修好了我描述的每一层，但"知道往哪挖"是我的。我理解工程师的价值正在从"能把代码写出来"迁移到"能保证正确的代码被交付出来"，而我是在新范式下完整跑通这个闭环的人。
